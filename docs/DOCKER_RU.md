# DiveFuzz в Docker: принцип работы, развёртывание, краевые случаи и диагностика

Этот документ дополняет `README.md` (раздел "Run with Docker") и описывает фаззер
с точки зрения внутренней механики, а не только команд запуска. Все пути,
переменные окружения и флаги ниже соответствуют коду в этом репозитории на
момент написания документа (ветка после Dockerization, см. `Dockerfile`,
`docker/`, `fuzzer/`).

---

## 1. Принцип работы

### 1.1 Общая идея

DiveFuzz — фаззер инструкций для RISC-V CPU. Его отличие от классических
инструкционных фаззеров в том, что он не просто генерирует случайные
последовательности инструкций, а **диверсифицирует значения, записываемые
инструкциями в регистры (write-back values)**. Это делается для того, чтобы
один и тот же шаблон инструкций проверял CPU в разных, ранее не встречавшихся
комбинациях состояний регистров, а не в одной и той же "типичной" комбинации.

Диверсификация технически реализована через **Spike** (эталонный RISC-V ISA
simulator) в модифицированной форме — `ref/riscv-isa-sim-adapter`. Это не
обычный Spike, а форк с добавленным Python-биндингом `spike_engine`
(pybind11), который умеет:

- выполнять инструкции по одной с возможностью checkpoint/rollback;
- читать значения регистров (GPR/FPR) до и после выполнения инструкции;
- откатывать состояние, если сгенерированная инструкция не подошла
  (например, её write-back совпал с уже виденным).

### 1.2 Жизненный цикл одного запуска (`run_dut.py`)

Точка входа — `fuzzer/run_dut.py --config <yaml>`. Пошагово:

1. **Парсинг аргументов** (`argparse`, обязателен `--config`).
2. **Создание каталога `outputs/`** (`config/logger_config.py:create_output_dir`) —
   относительно текущей рабочей директории процесса, не относительно
   расположения скрипта.
3. **Загрузка конфигурации** — `Config.from_yaml()`
   (`fuzzer/config/dut_config.py`). YAML разбирается на две части:
   - `dut_target` — единственная цель (устройство под тестом): имя, число
     потоков, версия, тип differential reference (`diff_ref`), путь к
     эмулятору (`emu_path`) и шаблон команды запуска (`cmd`, содержащий `$1`);
   - `seeds` — список профилей сидов. Каждый профиль — это либо готовый файл
     (`path`), либо директория с фильтром по суффиксу (`input: dir`), либо
     генерируемый DiveFuzz-профиль (`input: divefuzz`).
4. **Цикл по профилям сидов** (`executor/dut_executor.py:run_dut_tests` →
   `run_single_test`):
   - если профиль — `GeneratedSeedConfig` с `input: divefuzz`, вызывается
     `setup_divefuzz()` и `run_divefuzz()` (см. 1.3–1.5);
   - если профиль — директория или одиночный файл, сиды берутся напрямую
     (файл конвертации в `.img` не выполняется — предполагается, что входные
     файлы уже в формате, который понимает DUT).
5. **Параллельный запуск сидов на DUT** через `ThreadPoolExecutor` с числом
   потоков из `dut_target.threads` (см. 1.6).
6. **Формирование отчётов** — по каждому сиду и итоговая сводка
   (`utils/results_reporter.py`), запись в `outputs/`.

### 1.3 Генерация сидов: режимы `generate` и `mutate`

`setup_divefuzz()` (`fuzzer/executor/divefuzz_adapter.py`) выполняет две вещи
перед генерацией:

- **Проверяет наличие toolchain** — по очереди вызывает
  `riscv64-unknown-elf-as/-gcc/-ld/-objcopy --version`. Если хотя бы один
  инструмент не найден в `PATH`, выбрасывается исключение и профиль сида
  падает целиком.
- **Проверяет переменную окружения `spike`** (именно нижним регистром, не
  `SPIKE` и не `PATH`) — если её нет, выводится предупреждение; если она есть,
  но не содержит подстроку `DiveFuzz`, тоже предупреждение (диверсификация не
  гарантированно работает). Это не останавливает выполнение — это только
  логическое предупреждение.

Затем строится `DiveFuzzArgConfig` (внутренний конфиг генератора) и
вызывается `run_divefuzz()`, которая в зависимости от `mode` вызывает:

- **`generate_instructions_parallel()`** — генерирует `seeds_num` новых
  тестов по `ins_num` инструкций каждый, используя выбранный
  `template_type` (архитектурный шаблон: `xiangshan`, `nutshell`, `rocket`,
  `cva6` и др. — см. `generator/asm_template_manager/constants.py`) и набор
  разрешённых расширений ISA (`allowed_ext_name`, см. 1.4).
- **`mutate_instructions_parallel()`** — берёт существующий корпус
  (`mutate_input`) и мутирует инструкции внутри него.

Оба пути работают параллельно через `ThreadPoolExecutor` с `max_workers`,
равным `divefuzz.threads` из YAML (это отдельный уровень параллелизма от
`dut_target.threads`, см. раздел 3).

### 1.4 Кодирование инструкций и фильтрация

Внутри генератора:

- **`instruction_encoder.py`** превращает символическое имя инструкции и
  операнды в машинный код, используя `instr_dict.json` и `arg_lut.csv` —
  это данные, сгенерированные из submodule
  `fuzzer/generator/reg_analyzer/riscv-opcodes` (репозиторий `riscv/riscv-opcodes`).
  Файл `instr_dict.json` **не входит в git** — он генерируется командой
  `make` внутри `riscv-opcodes` (это делает `Dockerfile` на этапе сборки
  образа, см. раздел 2.2).
- **`ext_list/allowed_ext.py`** определяет, какие группы расширений ISA
  (`INSTRUCTION_FORMATS`-ключи вроде `RV_I`, `RV_M`, `rv_zifencei`, `rv_zbs`)
  разрешены для конкретного профиля (`allowed_ext_name`: `xiangshan`,
  `nutshell`, `rocket`, `cva6`, `rv32`, `general`, `base` и т.д.). Обратите
  внимание: три ключа (`rv_zifencei`, `rv_zbs`, `rv_32B`) записаны в
  нижнем регистре — это исторически сложившийся, но рабочий формат; во всех
  профилях эти ключи реально используются (см. раздел 3 про upstream PR
  переименования ключей).
- **`bug_filter/`** — фильтрует известные проблемные комбинации инструкций
  для конкретной архитектуры (`architecture`: `xs`, `nts`, `rkt`, `cva6`,
  `boom`), чтобы не гонять фаззер на давно известных багах.

### 1.5 Диверсификация через Spike и устранение дублей

Если `dive_enable: true`, генератор при построении каждой инструкции:

1. Ставит checkpoint в `SpikeSession` (`generator/reg_analyzer/spike_session.py`,
   обёртка над `spike_engine`).
2. Выполняет кандидат-инструкцию внутри Spike.
3. Читает значения затронутых регистров **до** и **после** — вычисляет XOR.
4. Если такой XOR уже встречался (по данным `xor_cache`/
   `stateful_xor_cache.py`), Spike откатывается к checkpoint, и генератор
   пробует другую комбинацию операндов — до `MAX_MUTATE_TIME` попыток.
5. Если XOR уникален — состояние Spike подтверждается, инструкция попадает
   в итоговый `.S`-файл.

Именно на этом шаге `spike_engine` обязателен: без него (`dive_enable: true`
без собранного `spike_engine`) генератор поднимает `RuntimeError` ещё до
записи хотя бы одного сида. При `dive_enable: false` этот шаг полностью
пропускается, и `spike_engine`/`spike`/`dtc` фактически не требуются для
генерации (но всё равно проверяются toolchain-пробы, см. `docker/probe.sh`).

### 1.6 Конвейер ELF → IMG и передача сида в DUT

После генерации `.S`-файлов (`utils/elf_to_img.py:process_assembly_files`):

1. `riscv64-unknown-elf-as -march=<полный список расширений>` — ассемблирует
   `.S` в объектный файл `.o`. Используемая `-march`-строка жёстко зашита
   (см. `elf_to_img.py:40`) и включает `zfa` — отсюда требование к версии
   binutils, см. раздел 2.2 и раздел 4.
2. `riscv64-unknown-elf-ld -T <link.ld>` — линковка в `.elf` с фиксированным
   линкер-скриптом `generator/reg_analyzer/linker/link.ld`.
3. `riscv64-unknown-elf-objcopy -O binary` — извлечение чистого бинарного
   образа `.img` (без ELF-заголовков) — именно этот файл получает DUT.

Затем `dut_executor.py:run_single_seed()` для каждого `.img`-файла:

1. Строит команду: `dut_config.cmd.replace('$1', f'"{seed_path}"')` — путь
   к сиду подставляется **в кавычках**, поэтому пути с пробелами
   поддерживаются корректно.
2. Запускает её через `subprocess.run(..., shell=True, cwd=dut_config.emu_path,
   timeout=300)`. Обратите внимание на два ключевых момента:
   - **`shell=True`** — `cmd` интерпретируется командной оболочкой, поэтому
     в нём допустимы дополнительные флаги, пайпы и т.п., но также требует
     аккуратности при формировании YAML (см. раздел 3);
   - **`cwd=emu_path`** — команда в `cmd` (`./build/emu ...`) выполняется
     относительно `emu_path`, а не относительно текущей директории
     `run_dut.py`. Это значит, что относительный путь `./build/emu`
     разрешится корректно только если `emu_path` указывает ровно на корень
     DUT, где лежит `build/emu`.
3. Код возврата процесса интерпретируется буквально: `0` → `SUCCESS`, иначе
   → `FAILURE`. Истечение `timeout=300` секунд → `TIMEOUT`. Любое иное
   исключение (например, DUT не найден) → `ERROR`.

### 1.7 Логирование

Три уровня логов, все — в каталоге `outputs/` относительно рабочей
директории процесса (`config/logger_config.py`):

1. **Общий лог выполнения** — выводится напрямую в stdout/stderr процесса
   `run_dut.py`.
2. **Лог профиля сидов** —
   `outputs/{имя_конфига}-{имя_профиля}.log`.
3. **Лог конкретного сида** —
   `outputs/{имя_конфига}-{имя_профиля}_{имя_файла_сида}.log` — содержит
   полный stdout/stderr самого DUT (включая, для RTL-симуляторов вроде
   Spike/Verilator, потактовые отладочные дампы — такие логи могут быть
   очень большими, см. раздел 3).

## 2. Инструкция по развёртыванию

### 2.1 Требования

- Docker Engine с BuildKit (проверено на версии 29.2.1).
- `git` и доступ к GitHub — сборка инициализирует два pinned submodule:
  `ref/riscv-isa-sim-adapter` и `fuzzer/generator/reg_analyzer/riscv-opcodes`.
- Свободное место на диске — ориентировочно 4 ГБ, и около 8 ГБ RAM на этапе
  компиляции Spike.
- Проверено и подтверждено только на `linux/arm64` (Apple Silicon). На
  `linux/amd64` версии apt-пакетов подтверждены как идентичные (через
  эмуляцию), но полная сборка/запуск на amd64 не проверялись.

### 2.2 Архитектура образа

Сборка двухэтапная (`Dockerfile`):

**Этап `builder`:**

1. Устанавливается toolchain для сборки Spike: `build-essential`, `g++`,
   `device-tree-compiler`, `libboost-regex-dev`, `libboost-system-dev`,
   Python 3 + `venv`.
2. Создаётся виртуальное окружение Python и в него ставятся зависимости из
   `requirements.txt`. Отдельно обходится известная проблема:
   **`PyYAML~=5.4.1` не имеет wheel-пакета для современных версий Python и
   не собирается из исходников под Cython 3** (ошибка
   `'build_ext' object has no attribute 'cython_sources'`). Решение —
   установка `Cython<3` и `--no-build-isolation` именно для PyYAML, прежде
   чем ставить остальные зависимости.
3. Копируется `ref/riscv-isa-sim-adapter` (pinned submodule) и собирается
   сам Spike (`./configure && make`), затем модуль `spike_engine`
   (`cd spike_engine && make`). Оба бинарника (`spike`, `spike_engine*.so`)
   проверяются на импортируемость/запускаемость прямо в момент сборки —
   если модуль не импортируется, сборка образа падает сразу, а не при первом
   реальном запуске.
4. Копируется `riscv-opcodes` (pinned submodule) и внутри него выполняется
   `make`, что генерирует `instr_dict.json` — файл, без которого
   `instruction_encoder.py` не может работать (см. 1.4).

**Этап `runtime`:**

1. Устанавливаются только runtime-зависимости: `python3`, `libstdc++6`,
   `libboost-regex`/`libboost-system` (динамические библиотеки, нужные
   `spike`/`spike_engine`), `device-tree-compiler` (пакет `dtc` — Spike
   обращается к нему **во время выполнения**, не только на этапе сборки, см.
   раздел 4), и toolchain `binutils-riscv64-unknown-elf` +
   `gcc-riscv64-unknown-elf`.
2. Копируются собранные артефакты из `builder`: виртуальное окружение
   Python, бинарник `spike`, каталог `spike_engine`, сгенерированный
   `riscv-opcodes` (с `instr_dict.json`), исходники `fuzzer/`, скрипты
   `docker/`, тесты `tests/`.
3. Настраивается окружение:
   - `PATH` включает каталог со `spike`, чтобы `command -v spike` работал —
     это соответствует тому, что описано в основном `README.md`;
   - **отдельно** выставляется переменная окружения **`spike`** (нижний
     регистр) — именно её реально читает
     `fuzzer/executor/divefuzz_adapter.py`, а не `PATH`. Значение указывает
     на бинарник и содержит подстроку `DiveFuzz` (путь установки —
     `/opt/DiveFuzz/...`), чтобы не срабатывало предупреждение "diversity
     may not work" (см. 1.2, раздел 3).
4. Создаётся непривилегированный пользователь `divefuzz` (uid 1000),
   рабочая директория — `/work`, точка входа —
   `/usr/local/bin/divefuzz` → `docker/entrypoint.sh`.

Версии всех apt-пакетов **зафиксированы явно** (`пакет=версия`) в
дополнение к фиксации базового образа по digest — это защищает от ситуации,
когда пересборка спустя месяцы тихо подтягивает другую версию `binutils`
или `gcc` при том же digest базового образа (сам digest фиксирует только
корневую файловую систему, а `apt-get install` без версии обращается к
живому зеркалу).

### 2.3 Сборка образа

```bash
./docker/build.sh
```

Скрипт:
1. Инициализирует **только** два необходимых pinned submodule (не трогая
   `dut/*` и `ref/riscv-isa-sim`, которые не нужны для сборки образа).
2. Если инициализация не удалась (нет сети) — завершает работу с понятным
   сообщением, а не проваливается где-то в середине `docker build`.
3. Выполняет `docker build -t divefuzz:latest .`

Для полностью чистой сборки без кеша:

```bash
./docker/build.sh --no-cache
```

### 2.4 Проверка зависимостей внутри образа

```bash
docker run --rm divefuzz:latest probe
```

Скрипт `docker/probe.sh` проверяет одним прогоном: версию Python (≥3.10),
импортируемость `yaml/numpy/psutil/tqdm/matplotlib/pybind11`, все четыре
`riscv64-unknown-elf-*` команды, `spike` в `PATH`, переменную окружения
`spike` (наличие, исполняемость, подстроку `DiveFuzz`), наличие `dtc`,
импортируемость `spike_engine`, наличие `instr_dict.json`, и что
`run_dut.py --help` отрабатывает.

### 2.5 Конфигурация запуска (YAML)

Конфигурация — обычный YAML в формате `demo.yaml.dev`/`demo.yaml.example`
(см. `README.md`). Для Docker важно только одно отличие от "голого" запуска
на хосте: **все пути внутри YAML должны быть путями внутри контейнера**, а
не путями хоста. В частности:

- `emu_path` — путь внутри контейнера к каталогу DUT (например,
  `/dut/XiangShan`), примонтированному через `-v`;
- `divefuzz.seeds_output` — путь под `/work`, чтобы результаты сохранялись
  в примонтированный том, а не терялись при удалении контейнера;
- `dir`/одиночные сиды (`path`) — тоже под `/work` или под смонтированным
  томом, если это внешние заранее подготовленные тесты.

### 2.6 Запуск

Базовый запуск с примонтированной рабочей директорией:

```bash
docker run --rm -v "$PWD/work:/work" divefuzz:latest --config /work/your_test.yaml
```

Другие команды точки входа (`docker/entrypoint.sh`):

```bash
docker run --rm divefuzz:latest --help     # справка CLI
docker run --rm divefuzz:latest probe      # проверка зависимостей
docker run --rm -v "$PWD/work:/work" divefuzz:latest smoke   # end-to-end smoke-тест
docker run --rm -it divefuzz:latest bash   # интерактивная оболочка
```

Точка входа устроена просто: если первый аргумент начинается с `-` (или
аргументов нет) — управление передаётся `run_dut.py`; `probe`/`smoke` —
отдельные встроенные скрипты; всё остальное выполняется как есть (полезно
для отладки, например `docker run --rm divefuzz:latest python -c "..."`).

### 2.7 Подключение реального DUT

Образ **намеренно не содержит** ни одного реального DUT (XiangShan,
NutShell, rocket-chip) — они собираются под конкретную версию отдельно (это
Chisel/Scala-проекты со своим тяжёлым тулчейном — mill/sbt, Verilator — и их
сборка не входит в область ответственности образа DiveFuzz). DUT
подключается bind-mount’ом:

```bash
docker run --rm \
  -v "$PWD/work:/work" \
  -v /host/path/to/XiangShan:/dut/XiangShan \
  divefuzz:latest --config /work/xiangshan.yaml
```

При этом `emu_path` в YAML должен указывать ровно на `/dut/XiangShan`
(путь внутри контейнера), а `cmd` — использовать относительные пути от
этого каталога (`./build/emu ...`).

### 2.8 Docker Compose

`compose.yaml` описывает три сервиса поверх одного образа — `divefuzz`
(по умолчанию `--help`), `smoke` и `probe`, все с одним и тем же volume
`/work`. Использование:

```bash
docker compose build
docker compose run --rm probe
docker compose run --rm smoke
docker compose run --rm divefuzz --config /work/your_test.yaml
```

### 2.9 Права доступа и non-root

Процесс внутри контейнера работает от непривилегированного пользователя
`divefuzz` (uid 1000). Если uid хоста отличается и bind-mount получается
недоступным для записи — либо запустить контейнер с
`--user "$(id -u):$(id -g)"`, либо использовать именованный Docker volume
вместо bind-mount (тогда прав хоста вообще не касается, см. также раздел 3
про сборку реальных DUT на bind-mount).

## 3. Краевые случаи (Corner Cases)

### 3.1 `gen_only` не останавливает выполнение на DUT

В `demo.yaml.dev`/`demo.yaml.example` есть закомментированный флаг
`gen_only: false` с пометкой "TODO: только генерировать сиды, не отправлять
на DUT". **Этот флаг парсится** (`config/dut_config.py:DiveFuzzConfig`), но
**нигде не используется** в реальном пути выполнения — ни
`divefuzz_adapter.py`, ни `dut_executor.py` его не читают. То есть при
`input: divefuzz` сиды **всегда** передаются на DUT после генерации,
независимо от значения `gen_only`. Если нужно только сгенерировать сиды без
запуска DUT — единственный надёжный способ на сегодня: указать в
`dut_target.cmd` заведомо безобидную команду (например, тот же
smoke-DUT-скрипт), либо явно доработать код.

### 3.2 `dive_enable: true` требует `spike_engine` и `dtc`, `dive_enable: false` — нет

При `dive_enable: false` шаг диверсификации (раздел 1.5) полностью
пропускается — не требуется ни собранный `spike_engine`, ни доступный во
время выполнения `dtc` (Spike вызывает `dtc` для построения device tree
именно в рантайме, а не на этапе компиляции — без него diversity-режим
падает с сообщением `Failed to run dtc`, и все сиды профиля "успешно"
генерируются в количестве нуля, без явной ошибки уровня процесса). Если вы
специально урезаете runtime-образ (например, для минимизации размера) —
удаление `device-tree-compiler` тихо сломает только diversity-режим,
обычная генерация продолжит работать.

### 3.3 ISA-профиль по умолчанию требует `zfa`, что требует binutils ≥ 2.44

`generator/config/config_manager.py` строит ISA-строку по умолчанию,
заканчивающуюся на `_zfa`. Ассемблер `binutils` версии 2.40 (Debian 12,
bookworm) не поддерживает `Zfa` и падает с ошибкой
`unknown prefixed ISA extension 'zfa'` на **каждой** инструкции при
`dive_enable: true` — при этом сама сборка образа проходит успешно, ошибка
проявляется только в рантайме при реальной генерации. Поэтому базовый образ
здесь — Debian 13 (trixie) с binutils 2.44. При адаптации Dockerfile под
другой базовый образ — обязательно проверять именно этот путь (не только
`--version` тулчейна, а реальную ассемблеровку с полной `-march`-строкой из
`elf_to_img.py`).

### 3.4 Совместимость differential reference с архитектурой хоста

Если `diff_ref` указывает на предсобранный x86-64 бинарник/библиотеку
(типично для готовых сборок NEMU/Spike-so, распространяемых вместе с
некоторыми DUT-репозиториями), а хост — `arm64` (Apple Silicon), библиотека
не подгрузится: `dlopen` завершится с ошибкой вида "cannot open shared
object file" (иногда без явного упоминания архитектуры — сообщение
одинаковое что для отсутствующего файла, что для несовместимого ELF).
Проверить заранее: `file <путь_к_.so_или_бинарнику>` на хосте — должен
совпадать с архитектурой контейнера (`aarch64`/`x86-64`). Если DUT
поддерживает флаг отключения дифференциального сравнения (например,
`--no-diff` у линейки XiangShan/NutShell/rocket-chip на базе `difftest`) —
можно запустить генерацию/выполнение без сверки с эталоном, но тогда
проверяется только факт исполнения (RTL реально выполнило инструкции и
дошло до определённого состояния), а не корректность результата относительно
эталона.

### 3.5 `$1`, кавычки и относительные пути

`cmd` в `dut_target` выполняется через `shell=True` с `cwd=emu_path`, а `$1`
заменяется на **путь сида в двойных кавычках**. Из этого следует:

- пути с пробелами в `seeds_output` (и, соответственно, в путях
  сгенерированных `.img`) работают корректно — кавычки уже добавлены кодом,
  добавлять их в `cmd` вручную не нужно;
- если `cmd` начинается с относительного пути (`./build/emu ...`), он
  разрешится **относительно `emu_path`**, а не относительно текущей
  директории `run_dut.py` или `/work` — частая ошибка при написании
  собственных конфигов;
- поскольку это `shell=True`, любые метасимволы shell в `cmd` (пайпы,
  переменные окружения, `&&`) интерпретируются буквально — это удобно, но
  требует того же уровня осторожности, что и с обычной shell-инъекцией, если
  `cmd` когда-либо строится из недоверенных данных (в текущем коде `cmd`
  берётся из локального YAML-файла, а не из внешнего ввода).

### 3.6 Таймаут на сид — 300 секунд, не настраивается через YAML

`dut_executor.py` жёстко задаёт `timeout=300` в `subprocess.run`. Если
реальный DUT (например, RTL-симулятор на большом количестве инструкций)
регулярно не укладывается в этот интервал — сиды будут попадать в
`ResultType.TIMEOUT`, и это не лечится изменением YAML-конфигурации, только
правкой кода `dut_executor.py`. Для быстрой диагностики стоит сначала
ограничивать сам DUT по числу тактов/инструкций (если он это поддерживает,
как многие RTL-симуляторы через флаги `-C`/`--max-cycles`), чтобы не
упираться в оба таймаута одновременно.

### 3.7 Генерация vs мутация

`mode: generate` создаёт `seeds_num` новых тестов с нуля. `mode: mutate`
требует уже существующий корпус в `mutate_input` — если каталог пуст или не
указан, мутация обработает пустой набор без явной фатальной ошибки на
уровне `run_dut.py` (сиды профиля будут отсутствовать, профиль завершится
с предупреждением "No seed files found").

### 3.8 `allowed_ext_name` и `architecture` — разные, но связанные настройки

`allowed_ext_name` определяет **набор допустимых расширений ISA** (что
вообще может быть сгенерировано), `architecture` — определяет, **какой
набор bug-фильтров** применяется (что специально исключается как известный
баг конкретного ядра). Это не одно и то же: например, для `rocket`
внутренний маппинг (`generator/config/config_manager.py`) переиспользует
фильтры `xs` (XiangShan), а не отдельный набор — потому что оба ядра
достаточно похожи по набору known-issues на момент написания фильтров.
Указание "экзотического" `architecture`, не входящего в явный маппинг,
просто передаётся как есть в `bug_filter.set_architecture()` — если такого
профиля фильтров не существует, поведение зависит от реализации конкретного
фильтра (может быть как "фильтров нет", так и ошибка на попытке
использовать несуществующий профиль — стоит проверять на малом наборе
сидов перед большим прогоном).

### 3.9 Два независимых уровня параллелизма

`dut_target.threads` — число потоков, которыми **сиды одного профиля
выполняются на DUT**. `seeds.divefuzz.threads` — число потоков, которыми
**сиды генерируются** (до передачи на DUT). Это разные пулы потоков и разные
стадии конвейера — увеличение одного не ускоряет другой. При тестировании
реального RTL-симулятора, который сам активно использует CPU/RAM, разумно
держать `dut_target.threads` небольшим (1–2), даже если генерация
запускается с большим числом потоков.

### 3.10 Особенности сборки реальных DUT (не самого образа DiveFuzz)

Хотя сборка реальных DUT (XiangShan/NutShell/rocket-chip) не входит в
ответственность образа `divefuzz`, при их подготовке для bind-mount
(раздел 2.7) на практике встречаются две категории проблем, характерные
именно для сборки Chisel/Scala-проектов внутри Docker:

- **Инструменты сборки типа `mill`/`sbt` держат фоновый демон поверх Unix
  domain socket.** Если исходники DUT смонтированы через bind-mount на
  Docker Desktop (macOS, virtiofs/osxfs), создание такого сокета может
  падать с ошибкой вроде `InvalidArgumentSocketException`/"Invalid
  argument" при попытке `bind()`. Решение — собирать DUT в контейнере,
  используя **именованный Docker volume**, а не bind-mount хостовой
  директории, и уже после сборки либо продолжать использовать тот же volume
  для запуска DiveFuzz, либо скопировать результат на bind-mount.
- **Несовместимость старого Scala-компилятора с новым JDK.** Если проект
  использует Chisel/Scala 2.13.x с версией, рассчитанной на JDK 11/17, а в
  окружении установлен более новый JDK (например, 21) — компиляция может
  падать глубоко внутри `scalac`/Zinc с ошибками парсинга classfile
  (`ClassfileParser`, `errorBadIndex` и подобные) ещё до того, как
  появится осмысленное сообщение о несовместимости версий. Решение —
  использовать именно ту версию JDK, под которую собран конкретный релиз
  Chisel (уточняется в `build.sc`/документации DUT), а не последнюю
  доступную в дистрибутиве.

## 4. Диагностика и устранение неполадок

| Симптом | Причина | Решение |
|---|---|---|
| `ref/riscv-isa-sim-adapter is empty in the build context` при сборке | Pinned submodule не инициализирован | Используйте `./docker/build.sh` (делает это автоматически), либо вручную `git submodule update --init ref/riscv-isa-sim-adapter` |
| `fuzzer/generator/reg_analyzer/riscv-opcodes is empty in the build context` | Та же причина, для второго submodule | `git submodule update --init fuzzer/generator/reg_analyzer/riscv-opcodes` |
| `spike_engine not available` / `import spike_engine` падает | Модуль не собран или собран под другую версию Python | Проверить `docker run --rm divefuzz:latest probe`; при самостоятельной пересборке — пересобирать весь образ, а не только модуль изолированно |
| `unknown prefixed ISA extension 'zfa'` при генерации с `dive_enable: true` | Слишком старый `binutils` (например, Debian 12/bookworm, версия 2.40) | Использовать базовый образ с `binutils` ≥ 2.44 (в этом репозитории — Debian 13/trixie, уже настроено) |
| `Failed to run dtc`, сиды генерируются в количестве 0 без явной ошибки процесса | Отсутствует пакет `device-tree-compiler` (`dtc`) в рантайм-образе | Установить `device-tree-compiler`; проверяется пробой `docker run --rm divefuzz:latest probe` |
| `Permission denied` при записи в `/work` | UID процесса в контейнере (1000, `divefuzz`) не совпадает с владельцем директории на хосте | Запустить с `--user "$(id -u):$(id -g)"`, либо использовать именованный volume вместо bind-mount |
| `Config file not found`, но процесс завершается с кодом 0 | Устаревшая версия `run_dut.py`, где `sys.exit(main())` был закомментирован | В этом форке исправлено — теперь код возврата корректно равен 1; если используется другая ревизия исходников, проверить `fuzzer/run_dut.py` |
| `AttributeError: 'DiveFuzzArgConfig' object has no attribute 'stateful_xor_cache'` при `input: divefuzz` | В `fuzzer/config/divefuzz_config.py` отсутствовали поля, которые безусловно читает `generator/config/config_manager.py` | В этом форке исправлено добавлением полей `stateful_xor_cache`, `bug_filter_enable`, `jump_enable` со значениями по умолчанию `True`; при использовании другой ревизии — проверить наличие этих полей |
| `cannot open shared object file` при использовании `--diff`/`diff_ref` с предсобранным reference-бинарником | Reference-библиотека собрана под другую архитектуру (например, x86-64) относительно хоста контейнера (например, arm64) | Проверить `file <путь_к_so>` — архитектура должна совпадать с архитектурой контейнера; при несовпадении собрать reference под нужную архитектуру или (если поддерживается DUT) запускать без дифференциального сравнения |
| `InvalidArgumentSocketException` / `Invalid argument` при первом запуске `mill` внутри контейнера | Инструмент сборки пытается создать Unix domain socket на bind-mounted (virtiofs/osxfs) директории | Собирать проект на именованном Docker volume, а не на bind-mount хостовой директории |
| Крах компиляции Scala глубоко внутри `ClassfileParser`/Zinc без внятного сообщения о версии | Несовместимость версии JDK с версией Scala/Chisel, под которую написан проект | Установить и явно указать (`JAVA_HOME`) более старую версию JDK, соответствующую требованиям конкретного релиза Chisel |
| Результаты и логи пропадают после завершения контейнера | `/work` не был примонтирован (`-v host:/work`) | Всегда запускать с volume/bind-mount на `/work`, если результаты нужны после остановки контейнера |
| Сид получает статус `TIMEOUT` | Выполнение на DUT превысило жёстко заданные 300 секунд (`dut_executor.py`) | Ограничить сам DUT по числу тактов/инструкций (если поддерживается), либо (при необходимости) изменить константу таймаута в коде |
| Профиль с `mode: mutate` не даёт сидов | `mutate_input` не указан или каталог пуст | Указать существующий, непустой каталог с корпусом в `mutate_input` |
| CLI выводит `--help`, но реальный запуск с `--config` тихо ничего не делает | Как правило — путь к конфигу или к сидам указывает на хостовый (не контейнерный) путь | Все пути в YAML должны быть путями **внутри контейнера**, соответствующими примонтированным томам (раздел 2.5) |
